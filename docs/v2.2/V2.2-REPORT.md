# LOWTIDE v2.2 — an operating plan in LOWTIDE

PHASE: v2.2 — the owner's whole operating plan (learning tracks, hackathons and CTFs,
products, content, money, deadlines) made structured and trackable, before the UI
redesign.

STATUS: PARTIAL. Everything is built, tested and committed on branch `v2.2`, and the
upgrade checks passed against the live data. The live swap was not performed: the
assistant's environment refused to stop and replace the running companion without the
owner's explicit go-ahead. Until the owner applies it, the live app runs v2.1, so Areas,
CTF kind and selection aren't live yet.

BUILT:

- **SPACE / Areas** (ADR-071): an eighth maintained section, after Projects, for ongoing
  tracks that aren't projects. The companion now makes the maintained sections at startup
  (never into an empty companion), so MCP can use a section an upgrade adds before the
  app opens SPACE. Workspace connections see and write Areas; Personal and College stay
  out of their scope.
- **Hackathon kind and selection** (ADR-072, schema V11): CTFs with their own rail
  (Registration → Preparation → Competition) and no PPT, build or "Track the build";
  the organisers' answer (applied, shortlisted, selected, rejected) on the sheet, the
  edit form, the list, MCP, the context pack and the workspace files.
- **The Claude Operating Guide** knows Areas, CTFs and that a database opens on its first
  saved view.
- **The owner's plan, as records** (ADR-070): entered over MCP into the live (v2.1)
  database after a named checkpoint, never committed: new projects with weighted
  milestones (none completed), an existing product's roadmap as milestones, dated tasks
  with subtasks, hackathons and CTFs, decisions (one superseding an earlier one), SPACE
  pages and databases with saved views in the projects' folders and a plan page with its
  shared databases, and imported databases extended (new properties, options, rows and
  views) without editing imported cells (checked cell by cell afterwards). Because Areas
  isn't live yet, the plan page sits in Ideas for now; moving it into Areas and marking
  the CTFs as CTFs are the two steps left after the upgrade.

CHANGED:

- `SPACE_ROOTS` gains `areas`; `companion/server/app.ts` ensures roots at startup;
  `kit.ts` opens Areas to workspace scope.
- `Hackathon.kind?`, `Hackathon.selection?`; repository, Zod schema, SQLite table spec,
  MCP tools, stage rail, sheet, form, list, context pack and workspace files.
- Docs: ADR-070 to ADR-072, DATA-MODEL (brought up to V11, including the V10 hackathon
  fields it was missing), OPERATING-PLAN, CHANGELOG, ROADMAP, STATUS, TESTING, README,
  and a correction to the formula list in SPACE-USABILITY.

MIGRATIONS:

- Dexie version 11, no upgrade function; nothing rewritten.
- Companion migration 8: `ALTER TABLE hackathons ADD COLUMN kind` and `selection`,
  nullable, each with its own CHECK; idempotent; the companion copies the database to
  `checkpoints/before-upgrade-8` first.
- Areas is a new section node, not a schema change.

TESTS: 77 files, 760 tests, all passing (743 before; 17 new across five new files and
migration 8 in `store.test.ts`). The startup test was checked to fail without the
startup change. `npm run e2e:companion`: 16 of 16 steps, schema 11 backups.

BUILD: `tsc -b` clean, ESLint clean, Prettier clean, `vite build` and the companion
build succeed (the two dynamic-import warnings predate this phase).

COMMITS: on branch `v2.2` (not merged into `main`, which the live app is served from).

LIVE UPGRADE: `scripts/upgrade-companion.mjs --check-only` against the running companion:
backup in `~/.lowtide/backups/` with integrity ok; the new build migrated a copy (schema
11, migrations 1–8, integrity ok, counts unchanged); the v2.1 build ran on the migrated
copy with counts unchanged. A separate scratch run confirmed the Areas section is added
and every existing section and hackathon is unchanged. Not done: the swap and the
fast-forward of `main`; they wait for the owner.

RISKS:

- In browser storage (no companion), an older app can't open a version 11 database, as
  with every version bump; the owner runs the companion.
- The full Vitest run is heavy under jsdom; two existing UI tests (the Command Room
  roadmap, the companion integration move) each failed once under full-suite load and
  passed on rerun and alone. Not caused by this phase; worth a look in the redesign.
- Areas is ordered by key in the app and by stored order then title over MCP; on an
  upgraded database it shares order 1 with Hackathons, so MCP lists Areas first by title.

NEXT: the owner reviews the plan in SPACE / Areas and issues the UI and task redesign
phase. Nothing of it was started.
